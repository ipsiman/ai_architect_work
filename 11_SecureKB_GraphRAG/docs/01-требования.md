# Техническое задание: SecureKB — защищённая база корпоративных знаний

«Защищённая платформа мультимодального анализа корпоративных знаний на графовых подходах».
Кодовое имя решения — SecureKB: RAG-система (Retrieval-Augmented Generation —
генерация, дополненная поиском) с гибридным поиском, графовым
расширением (GraphRAG-lite) и защитой данных на всех этапах обработки.
Требования проверены реализацией и отчётами этапов; архитектура, которая их
закрывает, описана в `docs/02-architecture.md`, план проекта — в
`docs/00-master-plan.md`.

## 1. Назначение и цели

Корпоративная база знаний объединяет документы разных уровней
конфиденциальности: публичные регламенты, внутренние проектные отчёты и
секретные материалы. Поиск по ключевым словам не отвечает на вопросы
естественным языком, а передача корпуса внешним облачным LLM-сервисам
(LLM — Large Language Model, большая языковая модель) недопустима: документы
содержат персональные данные и коммерческую тайну.
SecureKB закрывает обе задачи — отвечает на вопросы по корпусу со ссылками на
источники и полностью работает в закрытом контуре на локальных моделях, без
обращений к внешним API.

Вторая проблема — достоверность и утечки. LLM без ограничений склонна к
галлюцинациям и способна воспроизвести конфиденциальный фрагмент из документа,
недоступного спросившему. Поэтому система обязана отвечать только по найденным
и процитированным источникам, разграничивать доступ на уровне чанков, маскировать
персональные данные (PII) до индексации и на входе пользователя, отклонять
попытки prompt-инъекций и фиксировать события безопасности в журнале аудита.

Цели проекта (измеримы, проверяются критериями приёмки из раздела 6):
1. Ответы на русском языке по корпусу из 100 документов с цитатами на источники.
2. Разграничение доступа public / internal / secret на всех ветках поиска.
3. Качество golden-гейта не ниже 0.70 (факт — 0.87).
4. TTFT (Time To First Token — время до первого токена) не выше 5 с при одном
   параллельном запросе (факт — 3.08 с).
5. Блокирование атак без ущерба для легитимных запросов: инъекции отклоняются,
   корректные вопросы проходят.

## 2. Границы системы и роли пользователей

В границы системы входят: ингест документов (парсинг, чанкинг, PII-маскирование,
векторная и графовая индексация), RAG-чат с гибридным поиском и графовым
расширением, guardrails входа и выхода, RBAC (Role-Based Access Control —
доступ по ролям) с журналом аудита,
административный API, метрики, трейсинг и бэкап. Демонстрационный корпус —
100 синтетических документов на русском языке (50 public, 35 internal,
15 secret) с 24 находками PII; граф знаний — 20 узлов (10 персон, 5 проектов,
5 отделов) и 276 рёбер; 100 чанков и векторов.

За границами системы остаются: графический интерфейс (работа через REST/CLI),
обработка сканов и чертежей (мультимодальность сужена до текста), дообучение
моделей, продакшен-инфраструктура (кластеры, DMZ, секрет-хранилище). Эти
элементы отражены в целевой схеме развёртывания как направление развития.

Роли пользователей заданы тремя демонстрационными аккаунтами; уровни образуют
иерархию public < internal < secret:

| Пользователь | Уровень ACL (Access Control List — список контроля доступа) | Доступная часть корпуса |
|---|---|---|
| alice | secret | все документы |
| bob | internal | public и internal |
| guest | public | только public |

Правило доступа: пользователь видит чанк, если его уровень не ниже уровня
чанка. Правило действует во всех ветках поиска и дублируется контрольной
проверкой после слияния результатов (FR-11).

## 3. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Ингест корпуса: приём текстовых документов (txt/md) из каталога, 100 RU-документов, отчёт о прогоне |
| FR-02 | Чанкинг: разбиение документов на чанки по 500 слов с перекрытием 50 |
| FR-03 | PII-маскирование при ингесте (телефоны, e-mail, ИНН, паспорта) до эмбеддинга и записи в хранилища |
| FR-04 | Векторная индексация: эмбеддинги multilingual-e5-small (384 измерения, префикс passage:), точки Qdrant с payload acl и entities |
| FR-05 | Графовая индексация: извлечение сущностей по словарю (gazetteer), граф nodes/edges в SQLite, рёбра со-встречаемости |
| FR-06 | Гибридный поиск: плотный (Qdrant, префикс query:) и лексический BM25 (Best Match 25; реализация rank-bm25) |
| FR-07 | Графовое расширение запроса: сущности вопроса, соседние узлы графа, чанки связанных документов |
| FR-08 | Слияние результатов трёх веток методом RRF (Reciprocal Rank Fusion — обратное ранговое слияние; k=60) с детерминированным порядком |
| FR-09 | Генерация ответа локальной моделью Qwen2.5-1.5B-Instruct GGUF Q4_K_M (llama-cpp-python, Metal) с цитатами [N] на источники |
| FR-10 | Стриминг ответа по SSE (Server-Sent Events): sources, далее token, завершение done(cited_docs, retrieval_ms, ttft_ms); режим JSON без стриминга |
| FR-11 | RBAC на всех ветках поиска: pre-filter в Qdrant, per-ACL BM25-индексы, финальный контроль после RRF |
| FR-12 | Guardrails: InjectionGuard (RU/EN) и PII-маскировка на входе, OutputGuard (PII, чужие цитаты, маркеры SECRET) на выходе |
| FR-13 | Аудит событий query, injection_blocked, pii_masked, acl_drop, output_sanitized, answer в SQLite |
| FR-14 | Административный API: GET /admin/users, /admin/audit, /admin/stats |
| FR-15 | Наблюдаемость: метрики Prometheus (запросы, латентность, стадии, TTFT, токены, guardrail-события), трейсы OTel (OpenTelemetry) узлов графа в Jaeger, дашборд Grafana |
| FR-16 | Бэкап и восстановление: снапшот коллекции Qdrant и согласованная копия graph.db (sqlite3 .backup) |

## 5. Ограничения и допущения

Отступления от темы задания допустимы в рамках MVP (Minimum Viable Product —
минимально жизнеспособный продукт); целевые решения указаны в последней колонке.

| № | Отступление от темы задания | Ограничение | Допущение MVP | Снижение риска |
|---|---|---|---|---|
| О-1 | Мультимодальность сужена до текста | нет GPU-инференса VLM на рабочей машине | только txt/md | целевая схема: OCR-адаптер + Qwen-VL |
| О-2 | vLLM заменён на llama.cpp | vLLM требует Linux и NVIDIA GPU | локальный инференс, GGUF Q4_K_M | целевая схема: vLLM на GPU-нодах |
| О-3 | Neo4j заменён на SQLite | бюджет MVP, латентность LLM-экстракции | rule-based gazetteer, 20 узлов | целевая схема: Neo4j; польза графа доказана ablation-тестом |
| О-4 | GUI отсутствует | приоритет backend-функциональности | REST/CLI-клиент | целевая схема: веб-интерфейс поверх того же API |

## 6. Критерии приёмки

1. Автотесты: 129 тестов pytest проходят без ошибок.
2. Качество: golden Q/A гейт — 13/15 = 0.87 при пороге 0.70.
3. Польза графовой ветки: ablation recall@5 — 1.000 с графом против 0.944 без
   него; в пуле есть вопрос, решаемый только через граф.
4. Безопасность: red-team — 10 инъекций блокированы, 8 легитимных вопросов не
   заблокированы; недоступные чанки не попадают в контекст ни в одной ветке
   поиска (покрыто тестами ACL и defense-in-depth).
5. Нагрузка: SSE-стрим при конкурентности 1/2/4 — 0 ошибок; TTFT p50 3.08 с
   при пороге 5 с; рост латентности с конкурентностью объяснён сериализацией
   генерации (узкое место — LLM-инференс).
6. Наблюдаемость: метрики собираются Prometheus и отображаются на дашборде
   Grafana; трейсы узлов графа доступны в Jaeger.
7. Восстанавливаемость: бэкап создаётся одной командой; восстановление
   коллекции Qdrant из снапшота и файла graph.db из копии описано и проверено.
