# Отчёт по нагрузочному тесту (этап E2)

**Дата:** 2026-10-26. **Инструмент:** `scripts/load_test.py` (asyncio + httpx, без locust).
**Статус:** повторный прогон после исправления потокобезопасности LLM-генерации (LLM — Large Language Model, большая языковая модель; сериализация стримов инстанс-локом в `QwenLLM`).

## Стенд

| Компонент | Детали |
|---|---|
| Машина | Ноутбук Apple Silicon arm64 (darwin 24.6.0), MPS/Metal |
| LLM | Qwen2.5-1.5B-Instruct GGUF Q4_K_M (~1 ГБ), llama-cpp-python, `n_gpu_layers=-1`, локально в процессе uvicorn (один инстанс, один воркер) |
| Векторная БД | Qdrant в Docker на той же машине (контейнер securekb-qdrant) |
| Прочее | FastAPI + SSE (SSE — Server-Sent Events, потоковая передача событий); эмбеддер e5-small; Jaeger/Grafana не поднимались (не влияют на путь запроса) |

## Методика

- Уровни конкурентности выполняются последовательно; каждый воркер (asyncio, semaphore=конкурентность) непрерывно отправляет POST `/api/chat` до конца интервала duration.
- Вопрос — случайный из `data/golden_qa.json` (18 шт., фиксированный seed → воспроизводимо); `user_id` ротируется alice/bob/guest.
- Прогрев: 1 warmup-запрос перед замерами (первый вызов грузит модель и индекс BM25 (Best Match 25) в память), в статистику не входит.
- Метрики: total-латентность (до `done`/JSON), TTFT (Time To First Token — время до первого токена; по первому `event: token`), число token-событий; перцентили p50/p95/p99 линейной интерполяцией.
- Прогоны — после исправления потокобезопасности: stream — 45 с (c=1) и 30 с (c=2, c=4); non-stream — 30 с (c=1, 2, 4).
- Клиент останавливает уровень после 20 ошибок подряд (сервер недоступен) — в повторном прогоне ни один уровень не прерывался.

## Наблюдения

- Сбой в первом прогоне и его исправление. При concurrency≥2 в stream-режиме uvicorn падал (SIGSEGV exit 139, SIGABRT exit 134; в логе — `RuntimeError: llama_decode returned -1`). Причина: Starlette исполняет синхронные SSE-генераторы в threadpool → два потока параллельно вызывали `decode()` одного общего llama.cpp-контекста, который не потокобезопасен. Исправление (MVP — Minimum Viable Product, минимально жизнеспособный продукт): `QwenLLM.generate_stream` возвращает генератор-обёртку, держащую инстанс-`threading.Lock` весь жизненный цикл стрима — генерация сериализована (один одновременный генератор на процесс, остальные ждут в очереди). Следствие: параллельные стримы больше не роняют процесс (0 ошибок на c=2 и c=4), но латентность очереди растёт почти линейно с конкурентностью (c=2 ≈ ×2, c=4 ≈ ×5 к p50), RPS (Requests Per Second — запросов в секунду) не растёт. Целевое решение: vLLM с continuous batching — параллелизм без сериализации (потокобезопасный слой генерации из коробки).
- Насыщение с первого конкурентного запроса. Stream c=2: p50 total 3498 → 7308 мс (×2.1), TTFT 3080 → 7104 мс; c=4: p50 ≈ 17.2 с (×4.9), т.е. запрос фактически ждёт всю очередь впереди себя. RPS при этом плоский (0.270 → 0.265 → 0.234): генерация полностью сериализована в одном llama.cpp-контексте, конкурентность не добавляет пропускной способности — только очередь.
- TTFT ≈ 85–96% total (3080 из 3498 мс p50 при c=1). Замер stage-латентности на «свежем» вопросе: retrieval (Qdrant+BM25+граф) ≈ 20–48 мс (~1%), TTFT ≈ 2520 мс (prefill промпта с контекстом RAG; RAG — Retrieval-Augmented Generation, генерация, дополненная поиском), декод ~26 фрагментов ≈ 300–1300 мс. Узкое место — инференс LLM (prefill + decode) на одном GPU-контексте, retrieval пренебрежим.
- Эффект KV-кэша llama.cpp: повтор того же вопроса — total ≈ 425 мс (ttft ≈ 140 мс) против ~2.8–3.7 с на новый; в нагрузке вопросы разные, кэш не спасает.
- Stream и non-stream при c=1 почти идентичны (3498 против 3788 мс p50) — стриминг не ускоряет total, но отдаёт первый токен раньше (выигрыш в UX при длинных ответах).
- После исправления stream при c=2/4 устойчив: падений нет, сервер пережил все уровни без рестарта (в логе — только WARN/ERROR экспорта трейсов в неподнятый Jaeger, на путь запроса не влияют).

## Вывод: узкое место

Узкое место — LLM-генерация в однопроцессном llama.cpp: один общий контекст обслуживает запросы последовательно (теперь это закреплено явно — инстанс-лок в `QwenLLM`), поэтому конкурентность превращается в очередь: p50 растёт ×2.1 при c=2 и ×4.9 при c=4, RPS плоский ~0.21–0.27. Retrieval-стек даёт ~1% латентности и насыщения не создаёт. Потолок MVP ≈ 0.27 RPS (~16 запросов/мин) на один инстанс — но теперь без риска падения процесса при параллельных стримах.

Экстраполяция на целевую архитектуру (vLLM + GPU): непрерывный батчинг (continuous batching) и PagedAttention устраняют оба ограничения — запросы декодируются общими батчами (кратный рост RPS на той же GPU: десятки–сотни одновременных стримов), а PagedAttention снимает проблему разных контекстов; TTFT при свежем KV/prefix-кэше RAG-промптов падает до десятков–сотен мс. Качественный сдвиг: от «1 запрос в момент» (MVP-лок) к батч-мультиплексированию; vLLM даёт потокобезопасный слой генерации из коробки. Точка отказа, закрытая в MVP сериализацией, в целевой архитектуре исчезает вместе с самой сериализацией.

## Воспроизведение

```bash
docker compose -f infra/docker-compose.yml up -d qdrant
uv run uvicorn backend.app.main:app --port 8000 &   # дождаться /health
uv run python scripts/load_test.py --duration 45 --concurrency 1 --stream true
uv run python scripts/load_test.py --duration 30 --concurrency 2,4 --stream true
uv run python scripts/load_test.py --duration 30 --concurrency 1,2,4 --stream false
```

## Оговорки

- Ноутбук, docker (Qdrant) и клиент на одной машине — взаимное влияние замеров; заряд/термо не контролировались.
- Синтетическая нагрузка: 18 вопросов из golden-пула, короткие ответы (~22–26 фрагментов) — реальные ответы длиннее, decode-доля вырастет.
- Малая выборка на уровень (8–13 запросов): p99 информативен ограниченно.
- Уровни c=2/4 (stream) и весь non-stream прогонялись с duration=30 с, stream c=1 — 45 с (сопоставимо с первым прогоном).
- Метрики Prometheus/Jaeger в прогоне не собирались (стек не поднимался), латентности стадий — из `done.timings` и логов.
