# ADR-001: Движок LLM-инференса

**Статус:** Принято (2026-10-26).

## Контекст

Генерация ответов RAG-конвейера должна выполняться локальной инструктивной моделью.
Ограничения стенда и задания:

- закрытый контур: обращения к внешним API исключены;
- рабочая машина — macOS на Apple Silicon (Metal), дискретного NVIDIA GPU нет;
- суммарный бюджет моделей — менее 2 ГБ (LLM + эмбеддер);
- корпус и вопросы на русском языке: модель должна уверенно отвечать по-русски;
- ответы передаются клиенту стримингом (SSE — Server-Sent Events, потоковая
  передача событий), метрика TTFT (Time To First Token — время до первого токена) — критическая;
- один процесс API обслуживает несколько конкурентных запросов.

Замер этапа E2 подтвердил: инференс LLM — узкое место всего конвейера
(TTFT занимает ~85–96 % полной латентности, retrieval — около 1 %).

## Рассматриваемые альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| vLLM | Continuous batching, PagedAttention, десятки параллельных стримов, prefix-кэш | Требует Linux и NVIDIA GPU, отдельный сервис | Не запускается на стенде MVP (Minimum Viable Product, минимально жизнеспособный продукт; отступление О-2) |
| SGLang | Высокая пропускная способность, оптимизации графов исполнения | Те же требования: Linux + NVIDIA GPU | Не запускается на стенде MVP |
| TGI (Hugging Face) | Готовый REST-сервис инференса, квантование | Docker-контейнер, рассчитан на GPU-фермы | Не запускается без NVIDIA GPU, лишний сетевой сервис в контуре |
| ollama | Простая установка, управление моделями, REST из коробки | Меньше контроля над шаблонами промптов, форматом стриминга и параметрами генерации; отдельный демон — дополнительная точка отказа | Потеря контроля над шаблоном чата Qwen и стримингом; труднее воспроизводимые тесты |
| llama-cpp-python | Работа в процессе приложения, нативный Metal, полный контроль GGUF (GPT-Generated Unified Format), шаблона, сэмплеров и стриминга | Один контекст на процесс, нет батчинга | — |

## Решение

Принято: **llama-cpp-python + Qwen2.5-1.5B-Instruct GGUF Q4_K_M (1.04 ГБ)**, все слои
на Metal (`n_gpu_layers=-1`), модель загружена в процессе uvicorn (one-process, один
воркер). Qwen2.5-1.5B — лучшее качество русского языка в классе до 2 ГБ; квантование
Q4_K_M — компромисс качества и памяти, аналог подхода AWQ (Activation-aware Weight
Quantization) для CPU/Metal.

Потокобезопасность: контекст llama.cpp не допускает параллельный `decode()`, поэтому
генератор стрима держит инстанс-лок (decode-lock) весь жизненный цикл — генерация
сериализована, параллельные стримы не роняют процесс. Критерии выбора: соответствие
ограничениям (единственный вариант с Metal без внешних сервисов), MVP-бюджет
(1.04 ГБ из 2 ГБ), расширяемость (интерфейс генератора не привязан к llama.cpp).

## Последствия

**Плюсы:** нулевая инфраструктурная нагрузка (нет отдельного сервиса инференса),
полный контроль над промптом и стримингом, детерминированные тесты, 0 внешних вызовов.

**Минусы и риски:** пропускная способность ограничена одним контекстом — RPS
0.234–0.270 при конкурентности 1/2/4, p50 растёт ×2.1 (c=2) и ×4.9 (c=4);
узкое место — prefill промпта с RAG-контекстом (TTFT p50 3.08 с при c=1);
квантование Q4_K_M незначительно снижает качество по сравнению с полными весами.

**Целевая архитектура:** vLLM на GPU-ноде с AWQ-квантованием: continuous batching
и PagedAttention снимают сериализацию (кратный рост RPS, десятки одновременных
стримов), prefix-кэш RAG-промптов снижает TTFT до сотен миллисекунд. Переход
локализован адаптером LLM-интерфейса.
