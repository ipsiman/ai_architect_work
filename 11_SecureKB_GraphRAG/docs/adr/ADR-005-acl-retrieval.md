# ADR-005: Контроль доступа (ACL) в retrieval

**Статус:** Принято (2026-10-26).

## Контекст

Корпус содержит документы трёх уровней конфиденциальности (public / internal /
secret), правило доступа — иерархическое: пользователь видит чанк, если его уровень
не ниже уровня чанка (alice=secret, bob=internal, guest=public). Утечка секретного
чанка в контекст LLM — критический отказ системы, при этом кандидат проходит три
независимые ветки поиска (плотную, лексическую, графовую), каждая — отдельная
точка ошибки фильтрации. Ограничения: closed-loop, аудит обязателен (FR-13),
корректность проверяется автотестом на всём конвейере, а не только в плотном поиске.

## Рассматриваемые альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| Только post-filter (фильтрация результатов после поиска) | Простая реализация, одно место контроля | Одна ошибка фильтра — утечка: недоступные чанки уже получены из поиска и участвуют в слиянии/логах | Недопустимый риск для системы с секретным контуром |
| Отдельная коллекция Qdrant на каждый уровень | Физическая изоляция уровней | Три коллекции, дублирование инфраструктуры и конфигурации; запрос обязаны знать все свои уровни; рост числа уровней — рост коллекций | Эксплуатационная сложность ×3 без выигрыша против payload-фильтра |
| App-фильтрация после поиска без аудита | Минимум кода в ветках поиска | Ошибки фильтрации невидимы: нет события аудита, нет диагностики, тихие утечки при регрессии | Требование FR-13 (аудит событий безопасности) не выполняется |
| Три контура defense-in-depth | Ошибка одного контура не ведёт к утечке; попытка обхода фиксируется в аудите | Больше кода и тестов | — |

## Решение

Принято: **три независимых контура ACL** (defense-in-depth):

1. **Pre-filter Qdrant:** плотный поиск всегда с payload-фильтром `MatchAny`
   по уровням acl ≤ user (ADR-002).
2. **Изоляция лексической ветки:** индексы BM25 (Best Match 25) строятся отдельно на каждый
   ACL-уровень — чанки чужого уровня физически не входят в индекс пользователя;
   графовая ветка фильтрует соседей по allowed_doc_ids (ADR-004).
3. **Финальный контроль после слияния методом RRF (Reciprocal Rank Fusion):** перед подачей контекста в LLM каждый
   чанк перепроверяется на уровень; несоответствие — чанк отбрасывается,
   фиксируется событие `acl_drop` в audit_log.

Критерии: соответствие ограничениям (аудит и проверка на всём конвейере),
бюджет MVP (Minimum Viable Product — минимально жизнеспособный продукт;
фильтры на существующих механизмах Qdrant, BM25 и SQLite), расширяемость
(добавление уровня — одна константа иерархии).

## Последствия

**Плюсы:** недоступные чанки не попадают в контекст ни в одной ветке (подтверждено
test_security_e2e: bob без secret); третий контур выявляет гипотетические ошибки первых
двух и оставляет след в аудите; на легитимных пользователей схема не влияет.

**Минусы и риски:** тройная логика требует дисциплины при изменениях (любая новая ветка
поиска обязана встраиваться во второй контур и покрываться третьим); события
`acl_drop` в норме отсутствуют — их появление трактуется как регресс.

**Целевая архитектура:** контуры сохраняются; вынос проверки в отдельный
authorization-сервис с централизованной политикой (OPA-подобный слой), аудит —
в неизменяемое хранилище журналов вместо SQLite.
